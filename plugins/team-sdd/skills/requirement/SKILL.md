# Team SDD Requirement

将 PRD 转为可治理、可追溯的需求基线。Team SDD Core 是工作流权威；不要在对话中重建状态规则。

需求把关是写入基线之前的检查，不是另一条流程。不另建 Skill，不生成 slug，不把评审报告写到 Core 指定路径以外的文件。

## 工作流

1. 使用工作区绝对路径、`deliveryId` 与可用能力调用 `sdd_get_context`。只能写入 Context 返回的产物路径。
2. 阅读 PRD、原型、变更请求与仓库上下文。忠实记录来源，区分已确认事实与假设。
3. 按下面的「需求把关」检查材料。检查结论写入既有章节，不新增 Core 模板之外的必需章节。
4. 使用 Context 模板写入：`来源`、`需求理解`、`范围`、`业务规则`、`问题`、`答复`、`需求基线`。
5. 先从 PRD 的“需求编号 / 功能点编号 / 规则编号”等标注字段、Markdown 表格、标题、列表和重复编号模式中识别来源编号。识别到时，逐字保留为 `- 编号：<原始值>`；不要创建并行的 Team SDD 编号，也不要改变其拼写或格式。
6. 仅当来源项没有可识别编号时，分配递增的 Team SDD 编号；需求使用 `REQ-<数字>`，业务规则使用 `BR-<数字>`，并同样记录为 `- 编号：<值>`。
7. 对阻塞范围、规则、验收边界、权限、数据、兼容性或交付优先级的事实提出简洁问题。`问题` 中每项只标注 `状态：已解决` 或 `状态：未解决`，并在答复中记录确认结论。
8. 存在 `状态：未解决` 时，不得臆造答案或冻结需求基线。所有阻塞事实确认后，基线应成为精确的实现契约。
9. 仅在产物完成后调用 `sdd_submit_artifact`。若返回 Gate findings，先解决所列问题并更新产物，再次提交。不得编辑 Delivery 元数据或在没有明确授权时批准产物。产物中不得出现 `TBD` 或 `TODO`。

## 需求把关

按材料的复杂程度选择检查深度。不要求每个需求机械覆盖全部角度，但已经检查的项必须有证据。没有写出问题，不等于需求完整。

每项检查使用一个判断，写在对应段落或问题正文中，字段名用 `判断`：

- `通过`：已有明确证据支持。
- `存在问题`：发现遗漏、歧义、冲突或不可验证之处。
- `待确认`：现有材料不足，无法得出结论。
- `不适用`：与当前需求无关，并写明原因。

`判断：待确认` 不得写成 `状态：待确认`。材料不足而且会影响交付内容时，在 `问题` 中记录为 `状态：未解决`。建议、推测和默认假设不能写成已经确认的业务规则。影响业务流程、权限、安全、数据完整性或验收结果的问题，必须写明影响和后续处理方式。

材料足以判断时，至少核对这些角度：

- 当前业务问题、目标用户，以及本需求要改变的业务结果是否有依据。业务问题与产品方案分开写。
- 范围是否同时写明包含、不包含、参与者和边界。
- 来源之间是否一致。存在原型时，核对页面、字段、操作是否闭合、级联关系和角色；对不上的地方记为未解决问题，不补造页面或字段。
- 业务规则是否只收录已确认的规则和例外，并能追溯到来源编号。
- 验收边界是否能观察、能判定通过或失败。

`不适用` 写入 `范围` 的不包含项。`通过` 的证据写入 `需求理解`、`范围` 或 `业务规则`。只有 `存在问题` 和需要确认的 `待确认` 进入 `问题`。

## 质量要求

| 章节 | 必须达成的结果 |
| --- | --- |
| 来源 | 链接、引用或定位 PRD、原型与相关仓库证据。 |
| 需求理解 | 用可观察行为说明目标，而不是实现猜测。 |
| 范围与业务规则 | 明确包含、排除、参与者、边界、规则与例外；每个可追溯项记录 `编号：`。 |
| 问题与答复 | 保留从不确定性到确认结论的追溯关系。状态只有 `已解决` 和 `未解决`。 |
| 需求基线 | 形成可供 Design 和 Spec 拆分使用的稳定、可执行契约。存在未解决问题时不冻结。 |

## 需要暂停的情况

缺失的决定若会实质改变交付内容，应向请求方升级。例如导出数据范围、角色授权、保留策略或兼容性。缺少 Core Context、PRD 证据或必要用户决定时，可以完成发现工作但不提交。
