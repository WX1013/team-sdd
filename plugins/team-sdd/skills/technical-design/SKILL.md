# Team SDD Technical Design

将已批准的需求基线转为可实施的技术决策。Team SDD Core 负责活动状态、路径与 Gate 评估；不要以对话中的设计替代受治理产物。

本 Skill 适用于任何项目。不写入具体业务的页面、表名或参考仓库路径。当前交付如果指定了参考项目，只在该交付的设计产物里记录路径，并只借鉴其工程做法。

## 工作流

1. 使用工作区绝对路径、`deliveryId` 与可用能力调用 `sdd_get_context`。确认需求基线可用，只写入 Context 返回的设计产物路径。
2. 在选择方案前检查当前仓库的代码、运行时约束与既有契约。用户或交付指定了参考项目时，阅读该项目的分层、响应封装、迁移、字典和数据分类做法。
3. 完成 Context 提供的全部设计章节。背景、名词、模块依赖和外部数据写进这些章节，不另建第二份技术方案。
4. 在 `Requirement Coverage` 中，为每一项已覆盖需求逐字复制 `requirement.md` 的 `- 编号：<值>` 行。同一编号只保留一行。不得重新编号、简写或改变来源编号格式。
5. 将产品意图与技术选择分开。缺失或冲突的需求决定若改变可观察行为，应退回 Requirement 澄清。
6. Test Strategy 将关键行为与风险映射到可执行或可观察证据。变更既有契约时，Compatibility / Migration 说明发布、迁移与回滚。
7. 设计可执行后调用 `sdd_submit_artifact`。先解决所有 Gate findings 再重新提交。没有明确授权不得编辑 Delivery 元数据或批准产物。产物中不得出现 `TBD` 或 `TODO`。

## 数据分类

每项数据必须归入一类，并写明谁维护、本系统能否写入：

- 本地业务数据：本系统是权威来源，用当前仓库的迁移方式创建和变更。
- 外部推送或主数据：上游系统或数据开发维护。本系统只读，不把这些表放进本系统迁移，不在业务里回写。
- 本系统字典：只有需求明确允许本系统维护的字典才本地维护。被引用时能否删除，以需求基线为准。
- 展示冗余：可以保存名称便于列表展示，但统计和归属以基线指定的字段为准，不另造一套归属。

上游结构变化由数据方按现有业务口径兼容。本系统不因为上游多表就自行合并进外部表。

## 模块与接口

按可独立验收的业务能力划分模块，并写明依赖顺序。每个模块写清功能、失败时的可见结果、拥有的数据，以及接口的调用方、入参、出参和失败行为。

列表页展示字段由服务端组装后返回。导入按基线的匹配键更新已有记录并新增缺失记录；基线没有允许删除时，文件中未出现的旧记录保留。导出范围是当前筛选条件下的全部记录。需要文档生成时，沿用仓库已经选择的模板库，并写明没有模板时的界面状态。

## 实现约束

设计只记录本交付必须遵守的约束，不替代参考项目里的编码细则。

- 请求对象、响应对象和持久化对象分开。边界层只接收参数并返回统一响应，业务规则放在服务层。
- 一张本地业务表对应一个持久化入口，该入口不返回别的表的对象。统计查询可以单独存在。禁止把多个业务塞进一个公共持久化入口，禁止在循环中访问数据库或外部接口。
- 查询按场景编写，不复用一条覆盖所有筛选的语句。
- 当前仓库或指定参考项目如果要求审计字段，本地业务表包含主键、逻辑删除、创建人、创建时间、更新人和更新时间。创建时间和更新时间由数据库或现有自动填充处理，不由调用方传入。
- 标识使用英文。集合名体现集合。常量使用大写和下划线。同一语义只用一个名称。
- 方法参数超过五个时改为对象。批量写入放在一个事务里。
- 数据库方言以当前仓库为准。参考项目使用的字符集或分页写法不能直接套到另一种数据库。
- 前端沿用当前仓库的语言、组件库和样式方案。项目约定业务页面不使用另一种语言、不写页面单元测试时，设计不得引入它们。异步操作要有加载状态。重复出现的业务取值进入常量，不散落字面量。
- 不把参考项目的业务表、页面、账号、密码和令牌写入本交付。

## 停止条件

不得提交只复述需求、缺少关键技术决策、未说明调用方和失败行为的设计。仓库证据不足或参考项目与当前仓库冲突时，以已批准需求基线和当前仓库为准，并在设计中写明取舍。
